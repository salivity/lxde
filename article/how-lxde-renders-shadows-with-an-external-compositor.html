How LXDE Renders Shadows with an External Compositor

LXDE relies on a lightweight modular architecture where its default window manager, Openbox, handles window placement and controls without providing native composition. When paired with an external compositor like Picom or Compton, window drop shadows are created through off-screen redirection, blur convolution, and hardware-accelerated alpha blending via the X11 Composite extension. This article breaks down the exact rendering pipeline that transforms static Openbox frames into drop-shadowed desktop elements.

The Role of Openbox and the X Composite Extension

In a standard LXDE session, Openbox operates strictly as a traditional stacking window manager. It draws window decorations, title bars, and frames directly onto the X11 root window hierarchy, leaving no mechanism for soft transparency, translucency, or drop shadows.

When an external compositor starts, it registers as the composite manager on the X screen using the XComposite extension. The X server is instructed to redirect the rendering of all top-level windows into individual, off-screen pixmaps (storage buffers) instead of drawing them directly to the screen. Openbox continues to manage window coordinates, input events, stacking order, and window state, entirely unaware that the visual rendering has been intercepted.

Generating the Drop Shadow Geometry

Once window redirection is active, the external compositor inspects the X11 window tree to calculate shadow boundaries:

  1. Geometry Inspection: The compositor queries the window’s position, dimensions, and border attributes provided by Openbox and the underlying application.
  2. Shape Masking: If a window uses custom non-rectangular boundaries (such as rounded corners or shaped popups), the compositor checks the XShape or XFixes extensions to determine the exact outline.
  3. Shadow Mask Creation: An artificial alpha mask is generated based on the window's geometry. This mask is offset horizontally and vertically according to the user configuration file to simulate a light source direction.
  4. Blur Filtering: The compositor applies a blur algorithm—typically a box blur or Gaussian blur—to the edges of this offset mask. In an OpenGL backend, this is handled through fragment shaders; in an XRender backend, it is processed via CPU convolution or XRender convolution filters.

Compositing and Final Blending

With the window pixmaps and shadow textures prepared, the compositor constructs the final desktop image using back-to-front rendering (Painter’s algorithm) or unified scene graph passes:

  • Background Layer: The compositor draws the desktop wallpaper and LXPanel (unless configured to receive shadows itself).
  • Shadow Insertion: Before drawing a window, the compositor renders that window’s blurred shadow alpha mask into the composition buffer immediately behind the window's coordinates.
  • Window Contents: The window frame (rendered by Openbox) and client area (rendered by the application) are copied from their off-screen pixmaps and drawn directly on top of the shadow.
  • Alpha Blending: The compositor blends the semi-transparent pixels of the shadow with the underlying desktop elements using standard Porter-Duff compositing operators (such as Over).

Presentation to the Display

Once all layers, shadows, and windows are composed into a unified back-buffer, the external compositor presents the final frame to the physical display. Depending on the compositor's configuration, this output phase utilizes either the XRender extension or an OpenGL/EGL swap-buffer routine synchronized to the monitor's vertical refresh rate (VSync). This decouples LXDE's lightweight interface management from modern visual effects without requiring architectural modifications to Openbox itself.
