How LXDE Behaves in a systemd User Slice

Running the Lightweight X11 Desktop Environment (LXDE) inside a systemd user slice subjects its traditional, loosely coupled components to modern Linux cgroups control, unified process tracking, and strict resource management. While LXDE was not natively designed with systemd user targets in mind, encapsulating its session within a user slice alters how processes are grouped, monitored, throttled, and terminated, directly addressing legacy process-leak issues at the expense of requiring manual configuration for granular service supervision.

Cgroup Containment and Resource Allocation

By default, launching an LXDE session via a traditional display manager or startx places the entire environment under the general user session scope (session-N.scope). When explicitly executed within a dedicated systemd user slice (such as app.slice or a custom lxde.slice under user@<uid>.service), all child processes spawned by the session manager (lxsession) inherit that slice's control group parameters.

This allows system administrators to enforce strict limits on the desktop environment:

  • Memory Limits: If MemoryMax or MemoryHigh is defined on the slice, memory leaks from components like pcmanfm (desktop manager) or lxpanel are contained, preventing out-of-memory (OOM) conditions from destabilizing the entire OS.
  • CPU and I/O Shares: Systemd throttles the slice according to specified weights, ensuring background user workloads do not monopolize CPU time or storage bandwidth.
  • Task Constraints: TasksMax prevents fork-bombs or rogue shell scripts launched from within LXDE from exhausting system-wide process IDs.

Process Tracking and Session Lifecycle

LXDE relies on lxsession to start standalone binaries sequentially, including the Openbox window manager, taskbar, notification daemons, and polkit agents. In an unmanaged environment, background daemons often remain active as orphans if the X server crashes or terminates abruptly.

When confined to a systemd user slice, the lifecycle of these processes is bound to the slice's lifecycle. If the slice or containing scope is terminated using systemctl --user stop <name>, systemd leverages the kernel cgroup tree to identify every child, grandchild, and double-forked process spawned during the session. It issues a SIGTERM followed by a SIGKILL to the entire tree, ensuring zero orphaned processes remain in memory after logout.

Lack of Native Systemd Unit Integration

Unlike modern desktop environments such as GNOME or KDE Plasma, LXDE has not been rewritten to break its architecture into native systemd --user units and targets (e.g., graphical-session.target). As a result, its behavior inside a user slice presents specific characteristics:

  • Monolithic Containment: Every component started by lxsession resides in the same slice or sub-scope unless an application launcher explicitly uses systemd-run to place external apps into separate transient scopes. Consequently, an intensive application launched from the LXDE application menu competes directly for the slice's allocated quotas.
  • No Built-in Service Auto-Restart: Because components run as child processes rather than individual systemd user services, systemd cannot monitor or automatically restart individual failing elements, such as a crashed lxpanel, unless a third-party wrapper or custom unit configuration is implemented.
  • Compatibility Stability: Despite the architectural gap, running LXDE inside a user slice does not introduce internal IPC or X11 communication failures. The underlying D-Bus session and X socket operate transparently within the cgroup boundary.
