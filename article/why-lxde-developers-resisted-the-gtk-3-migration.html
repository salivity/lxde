Why LXDE Developers Resisted the GTK 3 Migration

When GNOME transitioned from GTK 2 to GTK 3, the Lightweight X11 Desktop Environment (LXDE) faced a critical crossroads regarding its underlying toolkit. While other desktop environments adopted the new toolkit, several core LXDE developers—most notably project founder Hong Jen Yee (PCMan)—strongly resisted a full migration to GTK 3. This resistance stemmed primarily from increased memory consumption, unstable application programming interfaces (APIs), design philosophies heavily biased toward GNOME, and a perceived loss of performance that clashed directly with LXDE's fundamental mission to remain an ultra-lightweight, resource-efficient desktop.

Ballooning Resource Footprint

The foundational goal of LXDE was to provide a full desktop experience with minimal CPU and RAM usage, making it ideal for aging hardware and resource-constrained devices like early netbooks and single-board computers. GTK 2 excelled in this environment due to its lean footprint.

When GTK 3 was introduced, it brought significant architectural shifts, including hardware-accelerated rendering, heavy reliance on Cairo, and modern styling mechanisms. These features substantially increased the memory and processing overhead of basic graphical widgets. For LXDE developers, adopting a toolkit that consumed visibly more RAM just to display a simple window directly undermined the project's identity.

API Instability and Maintenance Burden

During the early-to-mid GTK 3 release cycle, the toolkit frequently broke backward compatibility between point releases (such as moving from 3.4 to 3.6, and then to 3.8). Themes broke routinely, and core API behaviors shifted without long deprecation cycles.

LXDE was maintained by a relatively small, volunteer-driven team. The continuous churn of GTK 3 required developers to spend excessive time updating code simply to keep existing applications running on newer library versions, rather than implementing new features or fixing bugs. This maintenance overhead made a wholesale migration unsustainable for the team.

GNOME-Centric Design Philosophy

As GTK 3 matured, it increasingly prioritized the design guidelines of the GNOME 3 desktop. Features such as Client-Side Decorations (CSD), oversized touch-friendly UI elements, and the deprecation of traditional window management conventions conflicted with the classic desktop paradigm that LXDE maintained.

The GTK development team often treated the toolkit as an engine tailored specifically for GNOME, rather than a neutral, universal application framework. LXDE developers felt alienated by this direction, as working around GNOME-specific design mandates added complexity to maintaining a traditional, modular desktop interface.

The Qt Comparison and the Birth of LXQt

The resistance to GTK 3 reached a turning point in 2013 when PCMan decided to test alternatives by rewriting PCManFM—LXDE's core file manager—in both GTK 3 and Qt.

The benchmark results were striking: the Qt-based prototype consumed less memory, rendered faster, and offered a more stable API than the GTK 3 port. This realization confirmed the developers' suspicions that GTK 3 was no longer suitable for ultra-lightweight systems. Instead of proceeding with the GTK 3 migration, key developers partnered with the Razor-qt project to build LXQt, an independent desktop powered by Qt, while leaving the classic GTK 2 version of LXDE in maintenance mode.
