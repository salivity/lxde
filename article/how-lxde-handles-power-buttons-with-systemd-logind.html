How LXDE Handles Power Buttons with systemd-logind

This article explains how the Lightweight X11 Desktop Environment (LXDE) interacts with systemd-logind to manage physical power button events. It covers the kernel-level event detection, the use of systemd inhibitor locks via D-Bus, and the delegation process between the desktop session and system-level shutdown routines.

The Event Flow from Hardware to Userspace

When a user presses a computer's physical power button, the motherboard firmware generates an Advanced Configuration and Power Interface (ACPI) event. The Linux kernel's ACPI driver catches this signal and translates it into an input event (KEY_POWER) via the Linux input subsystem (evdev).

Both systemd-logind and X11/desktop components can listen to these input events, creating a potential conflict if two distinct subsystems attempt to react to the same keypress.

The Role of systemd-logind

systemd-logind runs as a system-level daemon responsible for seat management, session tracking, and core power events. By default, systemd-logind monitors evdev directly. Its default behavior—defined in /etc/systemd/logind.conf via the directive HandlePowerKey=poweroff—is to initiate an immediate system shutdown whenever KEY_POWER is detected.

To prevent this default shutdown and allow a graphical desktop environment to present a confirmation dialog or custom action, systemd-logind provides an inhibition interface over the D-Bus system bus.

Inhibitor Locks via D-Bus

Desktop environments claim ownership of power events through inhibitor locks. An application requests a lock by calling the Inhibit method on the org.freedesktop.login1.Manager interface:

  • What: handle-power-key
  • Who: The name of the session manager or power management utility
  • Why: A short string explaining that the desktop environment handles the event
  • Mode: block

As long as an active process holds a valid file descriptor representing this lock, systemd-logind suppresses its internal HandlePowerKey action and leaves the event to userspace.

How LXDE Implements Power Management

Unlike full desktop environments like GNOME or KDE Plasma, LXDE is modular and intentionally minimal. It does not contain an all-in-one power daemon:

  1. Session Handling (lxsession): LXDE's session manager, lxsession, initializes the user session. In modern distributions running systemd, lxsession registers with systemd-logind as a graphical session.
  2. Power Manager Utility: Because LXDE lacks a native, complex power daemon, distributions typically bundle LXDE with a third-party utility, most commonly xfce4-power-manager.
  3. Taking the Lock: When xfce4-power-manager (or a similar tool configured in LXDE's autostart) launches, it requests a handle-power-key inhibitor lock from systemd-logind.
  4. Triggering the UI: When the power button is pressed, the power manager catches the X11 key event and displays the LXDE logout dialog (lxsession-logout) or executes a preconfigured action (such as sleep or prompt).

If no dedicated power management tool is running in the LXDE session, no inhibitor lock is registered. In this scenario, systemd-logind handles the physical keypress directly, resulting in the default systemd power action without showing LXDE's graphical prompt.

Returning Control to systemd

Once the user chooses an action within LXDE (for example, selecting "Shutdown" in lxsession-logout), LXDE does not shut down the hardware directly. Instead, it calls systemd-logind over D-Bus using methods such as org.freedesktop.login1.Manager.PowerOff() or Reboot(). systemd-logind verifies user permissions via Polkit and executes the systemd target to cleanly unmount filesystems and power off the machine.
