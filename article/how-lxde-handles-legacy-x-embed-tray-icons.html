How LXDE Handles Legacy XEmbed Tray Icons

The Lightweight X11 Desktop Environment (LXDE) handles legacy XEmbed system tray icons natively through the notification area plugin integrated into its default panel, lxpanel. Unlike modern desktop environments that rely exclusively on modern D-Bus-based notification protocols, LXDE utilizes the classical freedesktop.org System Tray Protocol. This implementation allows older applications using the XEmbed protocol to dock their icons directly into the panel as embedded X11 windows without requiring third-party bridging utilities or protocol translation daemons.

The System Tray Selection Mechanism

To register as the system tray on an X display, lxpanel claims ownership of an X selection atom named _NET_SYSTEM_TRAY_S<screen>, where <screen> denotes the current screen number. When an application targeting the legacy system tray protocol initializes, it searches for the owner of this atom.

Once the client locates the owner, it sends a client message event—specifically SYSTEM_TRAY_REQUEST_DOCK—to the lxpanel tray manager window. This message includes the X11 Window ID of the icon that the client wants to display.

XEmbed Window Reparenting

Upon receiving the dock request, lxpanel relies directly on the XEmbed protocol specifications:

  1. Reparenting: The panel calls the X11 function XReparentWindow to move the application's icon window into the panel’s tray container widget.
  2. Container Management: lxpanel manages the size and layout of the embedded window, enforcing standard tray dimensions (typically 24x24 pixels or dynamic based on panel thickness).
  3. Mapping: Once contained, the window is mapped and becomes visible on the screen alongside the other tray components.

Because the icon is an actual embedded window rather than an image or serialized data stream, the original client process retains direct control over drawing and rendering its tray contents.

Event Handling and Interaction

Interaction handling under XEmbed is delegated entirely to the client application. When a user clicks, hovers, or opens a context menu on an XEmbed icon in lxpanel:

  • Mouse and Keyboard Events: X11 routes input events directly to the client’s embedded window.
  • Menus: Context menus are drawn and managed directly by the client application process rather than rendered via a menu definition parsed by the panel.
  • Tooltips: The client handles its own tooltip logic via its native GUI toolkit (such as GTK2 or Qt4).

Advantages and Architectural Limitations

Because LXDE was built around GTK2 and the core X11 architecture, its native reliance on XEmbed provides seamless backwards compatibility. Legacy utilities, system monitors, and older proprietary software embed without visual degradation or communication latency.

However, this legacy handling introduces specific constraints:

  • Scaling Issues: XEmbed icons do not scale dynamically. In high-DPI (HiDPI) environments, icons from older applications appear disproportionately small or distorted.
  • Process Isolation: Because the tray icon is a live window rendered by the client, a hung or unresponsive client application can cause rendering artifacts or unresponsive zones within lxpanel.
  • Modern App Compatibility: Applications that strictly output the modern D-Bus StatusNotifierItem (SNI) protocol require intermediary bridges (such as snixembed) to be visible within LXDE's legacy-focused tray container.
